# 角色 3D 资产管线（提示词 → 生图 → 多视图 → 图生 3D → 绑骨）

> **状态**：现行（2026-09-13 校订，含多视图步骤）
> **适用范围**：`assets/models/<unit_id>.glb` 的全部产出
> **配套**：每名角色的设定与提示词见 `docs/character-<unit_id>.md`；工程红线见 `AGENTS.md`

---

## 0. 一句话

**五步走：写提示词 → ImageGen 出正面全身图 → ImageGen 出多视图 → 混元多视角图生 3D → Blender 无头绑骨。**

每一步都有硬前置。跳过或颠倒任何一步，都会在后续步骤炸掉（下方「踩坑记录」逐条对应）。

---

## 1. 管线总览

| 步 | 输入 | 产出 | 工具 | 关键约束 |
|---|---|---|---|---|
| 1 写提示词 | 设计文档 + `data/units.csv` 数值 | `docs/character-<uid>.md` §5 | — | 见 §2 |
| 2 生正面图 | 上述提示词 | `assets/refs/<uid>_front.png` | ImageGen（文生图） | **直立站姿、单兵器、全身不裁切** |
| 3 生多视图 | 正面图 | `assets/refs/<uid>_{back,left_front,right_front}.png` | ImageGen（图生图） | 视角变化小、持握关系一致 |
| 4 图生 3D | 正面图（+ 多视图，按需） | `<uid>_ai.glb` / `.obj` / `_preview.png` | 混元 HY-3D `hy-3d-3.1` | 多视角、base64 ≤6MB、日额度 5 次（网页版 20 次，见 §5.3.2） |
| 4.5 清网格 | `<uid>_ai.glb` | 去碎块的同名 GLB | `tools/mesh_clean_islands.py` | **先焊接再判岛**；多视图版常残留披风下摆碎片 |
| 5 无头绑骨 | 上一步的 GLB | `assets/models/<uid>.glb` | `tools/blender_rig_character.py` | 输入网格必须直立；**跑完先看 `PROP_CLUSTERS` 行判断兵器是否被认出** |

**为什么顺序不能颠倒**：第 2 步的站姿直接决定第 5 步能不能绑骨（下蹲姿会让硬编码骨架与真实网格差 3 倍）；第 3 步的多视图决定第 4 步能把多少背面/侧面信息真正重建出来——只送一张正面图，模型只能靠猜。

> ⚠️ **但第 3 步的实际收益已被实测证伪（见 §8.2 / §8.3）**：多视图相对单图的轮廓 IoU 均值增益 **+0.000 ~ +0.004**，仅背面与右侧方向稳定为正；**绑骨环节的兵器识别也毫无改善**（两版种子 6 vs 7，都没认出长矛）。**这一步现在是「按需启用」而非默认必做**：默认只送正面图下单图版；只有角色「背面有重要识别特征」时才补做多视图。仍保留为管线第 3 步，是因为它对这类角色确实有效、且不能事后补（图生 3D 的输入决定一切）。

## 2. 第 1 步 · 写提示词

每名角色一份 `docs/character-<uid>.md`，其中 §5「生成提示词」是后续所有生图输入的源头。写法要求：

- **先对齐 CSV**：体型 / 配色 / 武器 / 技能视觉母题要与 `data/units.csv`、`data/skills.csv` 的实际设定一致（例：林冲是骑兵、长枪 range 1–2 → 造型保留骑姿倾向、兵器必须是长柄）。
- **锁定美术风格**：本项目统一「国漫卡通，cel-shading 平涂上色，墨线勾边，纯浅灰色背景，无场景元素，无阴影投影，线条干净利落」。
- **显式排除**：把禁用元素写进提示词（例：林冲「无大面积金饰」），否则模型会自行加戏。
- **与同阵营角色做区分**：例：林冲是「匀称的武者」，鲁智深是「壮硕巨汉」，两者的体型描述必须互斥。

## 3. 第 2 步 · 生成正面参考图

用 ImageGen **文生图**，尺寸 `1024x1536`（竖向 2:3），质量 `high`。

**硬前置（踩过坑，违反必炸下游）**：

| 要求 | 原因 |
|---|---|
| **全身直立站姿** | 第 5 步骨架的腿骨位置是硬编码的（大腿 x=±0.055、脚骨 x=±0.06），下蹲/蓄力/马步会让双脚落在 ±0.2 → 绑骨必崩。鲁智深首版出了下蹲蓄力姿，重出才正常。 |
| **双臂自然下垂、不遮挡武器** | 手臂交叠会让网格粘连，绑骨时无法分离。 |
| **持械手握位必须在腰胯高度**（约身高 0.43–0.49） | 骨架手骨固定在 `x=±0.11, z=0.43–0.49`，而兵器识别的种子门槛是「到该骨段 < 0.10」。**手抬到胸口高度（z≈0.70）就必定落空 → 种子恒为 0 → 兵器一定识别不到。** 实测死因：安道全（举针）、吴用（双链）、李逵（双斧）种子都是 0；宋万首版「横刀当胸」同此。详见 §3.1 / §8.6。 |
| **兵器顶端不超过头顶** | 脚本把 `maxs.z - mins.z`（**含兵器**）归一化到身高 1.0，**并不单独识别人体高度**；而骨架坐标（`Head` z=0.88、`Hips` z=0.52、手骨 z=0.43–0.49）是按「人体=1.0」硬编码的。**兵器一过顶，人物在归一化空间里被压缩、骨架上下全错位。** 长枪/长柄武器必须写死「枪尖/刀尖朝上、顶端不超过头顶」。 |
| **兵器远离一切大面积布料**（下摆 / 围裙 / 披风 / 马尾） | 兵器识别是**空间洪泛**（KD 半径 0.06，仅靠 `_d_body>0.12` 阻断），一旦兵器贴着布料，洪泛会从兵器窜进布料，把「细长兵器」长成一坨布 → 长细比崩掉被丢弃。实测：扈三娘（柳叶刀→高衩下摆，长细比 2.1）、秦明（狼牙棒→朱红重甲，吞 12157 顶点）。 |
| **只出现一件兵器** | 多兵器会让重建结果出现重叠畸形。 |
| **不裁切、人物居中、纯色背景** | 图生 3D 依赖完整轮廓做前景分割。 |
| **长兵器与身体留出间隙** | 混元输出是「融合单面网格」，贴身持握的长兵器无法被自动识别成独立部件（详见 §8）。同时，间隙也是洪泛阻断生效的前提。 |

## 4. 第 3 步 · 生成多视图

用 ImageGen **图生图**（`image1` = 该角色的 `_front.png`，`input_fidelity: high`），逐张生成其余视角。

### 4.1 视角怎么选

| view_type | 评价 | 说明 |
|---|---|---|
| `back` | ✅ **必选** | i2i 表现最稳，背面信息（披风、后甲、发髻）完整。 |
| `left_front` / `right_front` | ✅ **推荐** | 3/4 近角。视角变化幅度小，手与兵器的接触关系能保住。 |
| `left` / `right` | ❌ **实测会崩** | 纯正侧视要求模型凭空想象整个侧面 + 手持兵器的空间关系。实测右视图把丈八蛇矛挪到身后、脱离手掌悬空立着，与正面图矛盾。 |
| `top` / `bottom` | ⚪ 未验证 | 本项目角色为直立站姿，俯视/仰视信息量低，暂不使用。 |

**核心原则：宁要一致的近角，不要崩掉的远角。** 一张角度保守但持握正确的 3/4 图，对重建是净收益；一张角度漂亮但兵器错位的正侧图，会把畸变直接焊进模型。

### 4.2 提示词模板

四段结构，逐段都要写死：

```
【视角变更】同一角色的<视角名>视角全身立绘，仅改变相机观察角度。
保持与参考图完全一致的角色外貌：<发型与冠帽、面部特征、甲胄形制与磨损、披风、束带、
配色与纹样、金属配件 —— 按该角色的设定逐项列出>。
相机绕到人物<左前方/右前方/正后方>约 <45> 度，人物本身的姿势、朝向、位置完全不变，
仍是直立站姿、全身入镜、居中构图。
<兵器名>必须保持与参考图完全相同的持握关系：<哪只手握、枪杆贴身体哪一侧、矛头朝向>。
绝对不得把兵器移到身后、不得悬空脱离手掌、不得改变持握手。
国漫卡通风格，cel-shading 平涂上色，墨线勾边，纯浅灰色背景，无场景元素，无阴影投影，线条干净利落。
```

第 3、4 段（姿势不变 + 持握关系）是**抗漂移的关键**，不能省。仅写「换个视角」时模型会自由发挥姿势与兵器位置。

### 4.3 生成后必做：去水印

ImageGen **无法关闭水印**（`footnote` 只能改文案，≤16 字），部分批次会在右下角压上「AI生成 / WORKBUDDY」。水印送进图生 3D 会被当作前景，生成悬浮碎块。

```bash
# 先只检查（不改文件）
python tools/nh3d_dewatermark.py --check assets/refs/<uid>_*.png
# 确认安全区没压到人物后执行（原图自动备份为 <name>.wm.bak.png）
python tools/nh3d_dewatermark.py --safe-x 0.84 assets/refs/<uid>_*.png
```

工具原理：安全区（默认自动取人物右边界 +15px，可 `--safe-x` 手动覆盖）内整块填充背景色。**之所以整块填而不按亮度逐像素判断** —— 半透明水印的边缘像素与背景差异远低于可用阈值，逐像素判断必留灰白鬼影（实测踩过）。

⚠️ **不要信自动的 `--safe-x`（2026-09-15 第三批 10 张实测）**：自动检测把**水印文字本身**也当成了「人物右边界」（水印也是深色墨线），于是算出的 safe_x 偏大，**水印左侧会残留约 9–20px**。正解是**先量再填**：

1. 量水印左边界（全批固定位置，实测 1024 宽图是 **x=903**）与角色最大 x（band `y≥0.88H`，第三批是 754–**881**）；
2. `--safe-x` 取两者之间 —— 第三批窗口只有 22px，取中点 **0.870**；
3. **填充后做两项数值验证**（不要只肉眼看）：
   - 安全区内重测暗像素 → 应为 **0**；
   - 安全区外与 `.wm.bak.png` 逐像素比对 → 应为 **0 处改动**。

⚠️ 填充不可逆，务必先 `--check`，处理后再目视复核人物是否被波及。
⚠️ 水印不是每批都有：同一批 `lin_chong_front.png` 干净，而同时生成的三张多视图都带水印。**逐图检查，不要靠推测。**

### 4.4 人工复核

生成完拼一张横向对比图，逐张确认：① 兵器是否被手握住、位置是否与正面图一致；② 配色与甲胄纹样是否一致；③ 是否有第二件兵器或多手。**有问题的视角直接弃用，不要凑数送进重建。**

## 5. 第 4 步 · 混元多视角图生 3D

### 5.1 命令

```bash
# 单张（仅正面图）
echo -n "<token>" | python tools/nh3d-gen3d.py submit assets/refs/lin_chong_front.png --faces 30000 --model 3.1

# 多视角（推荐：正面 + back + left_front + right_front）
echo -n "<token>" | python tools/nh3d-gen3d.py submit assets/refs/lin_chong_front.png \
    --views "back=assets/refs/lin_chong_back.png;left_front=assets/refs/lin_chong_left_front.png;right_front=assets/refs/lin_chong_right_front.png" \
    --faces 30000 --model 3.1

# 批量（限流排队 + 轮询 + 自动下载），注意 ; 要用引号包住
echo -n "<token>" | python tools/nh3d-drive.py assets/models \
    'lin_chong=assets/refs/lin_chong_front.png;back=assets/refs/lin_chong_back.png;left_front=assets/refs/lin_chong_left_front.png;right_front=assets/refs/lin_chong_right_front.png'

# 提交前先验载荷（体积 / 字段 / 视角），不真提交
echo -n x | python tools/nh3d-drive.py assets/models --dry-run 'lin_chong=assets/refs/lin_chong_front.png;back=assets/refs/lin_chong_back.png'
```

工具分工：

| 工具 | 职责 |
|---|---|
| `tools/nh3d_lib.py` | 共享库：本地图 → JPEG base64、组装多视角载荷、`view_type` 校验、6MB 门禁 |
| `tools/nh3d-gen3d.py` | 单次 `submit` / `status`，带 `--dry-run` |
| `tools/nh3d-drive.py` | 批量调度：并发上限 2、429 退避重试、轮询、自动下载 GLB/OBJ/预览图 |
| `tools/nh3d_dewatermark.py` | 参考图去水印 |

### 5.2 接口约束（HY-3D，全部实测/查证）

| 项 | 约束 |
|---|---|
| 模型 | 多视角**必须** `hy-3d-3.1`；`3.0` 不支持 `back`/`top`/`left_front`/`right_front` |
| 正面图字段 | `ImageBase64`（或 `ImageUrl`）—— 顶层的正面图 |
| 其余视角字段 | `MultiViewImages[].ViewImageBase64`（值可为「图片 url 或 base64 数据」→ 本地图可直连，**全程无需图床**） |
| `view_type` 枚举 | `left` / `right` / `back` / `top` / `bottom` / `left_front` / `right_front` —— **不含 `front`** |
| 每视角张数 | 1 张 |
| 体积 | 所有图 base64 编码后**总和 ≤ 6MB**；单边 128–5000px；jpg / png |
| 并发 | 本环境实测 concurrent slot limit = 2 |
| 日额度 | **5 次/天**（见 5.3） |

体积对策：本地图统一转 **JPEG（quality 88，长边 ≤1024）** 再 base64，单张约 0.13–0.20MB；四视角合计约 0.7MB，余量充足。

### 5.3 日额度（会卡住批量）

**额度语义（2026-09-13 实测查证）**：

- 硬限 **5 次提交/天**，超限返回 HTTP 429 `daily submit limit exceeded (5/5) for dimension hy-3d`。
- **按 `dimension=hy-3d` 计数，与模型版本无关** —— 3.0 与 3.1 共用同一个池子。实测：额度耗尽后提交 `model=3.0` 同样返回 `for dimension hy-3d` 的 429。→ 想用 3.0 探路再切 3.1，额度一样扣。
- **计数口径 = 提交次数**，与图片张数无关：单图提交、四视角多图提交，各算 1 次。任务失败是否返还额度未验证（额度检查发生在提交阶段）。
- **重置点 = UTC 00:00（北京时间 08:00），已两端闭合验证**：北京时间 2026-09-13 00:47（UTC 16:47）提交报满额；同一份四视角载荷在北京时间 2026-09-13 08:33（UTC 00:33）提交**成功**（job `1490509401353568256`）→ 重置确实落在 UTC 日界，不是北京 0 点。
- **客户端不可配置、不可查询**：`_PROVIDER_MAP["3d"]` 只暴露 submit / query 两个 action（provider `hy-3d`、service `ai3d`、version `2025-05-13`），没有额度查询接口；429 响应体也不含剩余次数或重置时间。
- → 排期结论：5 名英雄 = 5 次，**一天刚好一批**。动手前先算额度。
- ⚠️ **两条路径的重置点不是同一套，别混算**（2026-09-13 实测）：

  | 路径 | 上限 | 重置点 | 查询额度 |
  |---|---|---|---|
  | 内置 `hy-3d` | 5/天 | **UTC 00:00 = 北京 08:00**（已两端闭合） | ❌ 无接口，只能靠 429 反推 |
  | 网页版 | 20/天 | **北京 00:00（UTC+8）** | ✅ `POST /api/3d/quotainfo` → `{"date","totalQuota","alarmQuota","remainQuota","consumeQuota"}` |

  依据：网页版在北京 2026-09-13 02:14 用掉 1 次，当日 11:26（= UTC 03:26）查到 `{"date":"20260913","remainQuota":19,"consumeQuota":1}`。若按 UTC 日算，那一次应落在前一天、今日 `consumeQuota` 应为 0。→ 网页版记的是**北京日期**。
  网页版额度查询工具：`node tools/hy3d_web_quota.js [--raw]`（只读，不消耗额度）。

**想突破这个限制，三条路**：

| 方案 | 额度 | 成本 | 说明 |
|---|---|---|---|
| A 腾讯云官方混元 3D API | 按量计费，无日限 | 按调用付费 | 需自行开通腾讯云账号 —— 本管线走的就是腾讯云系（`tokenhub.tencentmaas.com` → `hy-3d` / `ai3d`） |
| B **本地部署开源 Hunyuan3D** | **无限次** | 仅电费 | ✅ 本机有 RTX 4090 + 已装 ComfyUI；见下方「本地替代方案」 |
| C 官方网页版 `3d.hunyuan.tencent.com` | **20 次/天** | 扫码一次 | **已打通**（`tools/hy3d_web_gen.js`）—— 详见 §5.3.2 |

### 5.3.1 本地替代方案（开源 Hunyuan3D）

腾讯把权重开源了（Apache 2.0，可商用）。官方 README 实测规格：

| 组件 | 参数量 | 显存 | 作用 |
|---|---|---|---|
| Hunyuan3D-Shape-v2-1 | 3.3B | 10 GB | 图 → 几何（可带单图或多视角） |
| Hunyuan3D-Paint-v2-1 | 2B | 21 GB | 几何 → PBR 纹理贴图 |
| 两者同时驻留 | — | 29 GB | ⚠ **超出 4090 的 24GB** |

**4090 跑法**：两阶段显存不叠加（Paint 阶段吃的是已生成的网格文件，不加载 Shape 模型）→ **分两步跑即可**，先出网格再做纹理。社区还有 fp16 / 量化权重（ComfyUI 版约 7.4GB 与 4.9GB），需求更低，单模型 30–90 秒。

**开源版本身也分两条路**，正好对应本管线的核心分歧：
- `Hunyuan3D-2.1`（单图）→ 带 PBR 纹理，质量高
- `Hunyuan3D-2.0-mv`（多视角，2–4 张）→ **仅几何、无纹理**，需另接纹理步骤

→ 也就是说，「多视图相对单图收益到底有多大」这个问题，本地可以**免费无限次**验证，不必再排额度。

**前提**：4090 上常驻的 `qwen38-27b` 服务占 23GB 显存，跑 3D 前必须先 `ssh 4090 'docker stop qwen38-27b'`。

### 5.3.2 网页版 `3d.hunyuan.tencent.com`（2026-09-13 已打通）

**登录**（无匿名入口）：

- 生成中 `modelUrl3d` 是空对象；**纹理阶段跑完**后 `result[0].urlResult` 才填齐。
- `textureGlb` / `glb` = 带 PBR 纹理的成品；`geometryGlb` = 仅几何（约 0.6MB）。
- 抓法：headless 打开 `/assets` 收集该接口响应 → 解析 → `ctx.request.get()` 带会话 cookie 取回。**这条路径不依赖任何按钮文案或坐标，页面改版也不容易崩。**

**网页自动化的四个坑（均已解决）**：

1. **点击必须用真实鼠标事件，不能用 `el.click()`** —— 最贵的坑。页面上 innerText 恰为「立即生成」的元素有 **3 层**：外层 `DIV`(depth5) → `BUTTON`(depth6) → `SPAN`(depth7)。`querySelectorAll` 按**文档序**返回（父在子前），朴素 `find()` 拿到的是最外层 `DIV`，而 `onClick` 挂在内层 `BUTTON` 上 —— 点 DIV 不会把事件向下传给 BUTTON，结果是**完全静默**：截图与点击前逐字节相同、一个请求都不发（实测就这样空转了 16 分钟）。正解：算出目标元素中心坐标 → `page.mouse.click(cx, cy)`，顶层命中到 BUTTON/SPAN，事件向上冒泡，handler 正常触发。
2. **顶栏「资产」点了不跳转**（SPA 导航问题）→ 必须 `goto /assets` 再看内容，别指望点菜单。
3. **JSON 里的 URL 带 `\u0026` / `\/` 转义** → 提取直链的正则**不能**把反斜杠排除在字符类外，否则会在第一个 `\u0026` 处截断，签名参数全丢、直链不可用。
4. **未登录时 `/` 会再跳一次 `/login`**（SPA 客户端重定向）→ 判定登录态**必须等 URL 稳定**（连续 1s 不变），否则会把跳转前的 `/` 误判为已登录。
   另有两个小坑：`filechooser` 事件不触发（兜底直接对第 i 个 `input[type=file]` 调 `setInputFiles`）；`添加多视图（Min2，Max8）` 这类带后缀按钮要「精确匹配优先 → 退化为最短包含匹配」并限制 `children.length ≤ 4`。

**风险**：网页端自标「3D Studio 新版 v1.2 | 全面公测」，UI 变动会让 `gen`（走 UI 那条）失效 —— 但 `pull`（读接口）不受影响；存在自动化风控，别高频刷。

**实测状态**：2026-09-13 **端到端跑通** —— 扫码登录 → 四视角提交 → 轮询 → 接口取回 10 个文件（成品 GLB 43.8MB + PBR 贴图组 + 预览图），额度 20 → 19，全流程约 7 分钟。

**横向结论**：

| 路径 | 额度 | 前置人工 | 稳定性 | 适用 |
|---|---|---|---|---|
| 内置混元（现状） | 5/天 | 无 | 高 | 小批量、验证 |
| **网页版自动化** | **20/天** | **扫码一次** | 中（`gen` 依赖 UI；`pull` 稳） | **多视图验证（已用此路跑完）** || 腾讯云自有 API | 按量可买 | 实名 + 付费 | 高 | 量产 |
| **本地开源 Hunyuan3D** | **无限** | 部署 | 高 | **量产首选** |

## 8. 已知局限与实测结论

### 8.1 混元输出是「融合单面网格」

单个 mesh、无部件语义，**且焊接后是单一连通壳体**（`tools/mesh_stats.py` 实测）：

| 模型 | 三角面 | 焊接前顶点 / 假岛 | 焊接后顶点 | 真实连通岛 | 最大岛占比 |
|---|---|---|---|---|---|
| `shiqian_ai.glb` | 30 000 | 21 710 / 672 | 14 988 | 1 | 100% |
| `wu_song_ai.glb` | 29 994 | 23 567 / 1042 | 14 951 | 1 | 100% |
| `lu_zhishen_ai.glb` | 30 004 | 23 688 / 1042 | 14 916 | 1 | 100% |
| `hua_rong_ai.glb` | 29 924 | 22 966 / 975 | 14 881 | 2 | 99.8%（另一岛 30 顶点） |
| `lin_chong_ai.glb`（单图） | 30 004 | 26 384 / 1702 | 14 898 | 1 | 100% |
| `lin_chong_mv.glb`（**多视图**） | 50 000 | 41 154 / 2179 | 24 950 | 1 | 100% |

> ⚠️ **纠正早期说法**：此前本文写的「897 个连通岛屿」是**未焊接**计数。GLB 导入后顶点会被 UV/法线接缝拆开（例：50 000 面 / 41 154 顶点，平均价数仅 2.4），按边连通数出来的「岛」绝大多数是接缝碎片，不是真实几何岛。**数岛屿前必须先 `remove_doubles` 焊接**（`tools/mesh_stats.py` 已内置，阈值 0.0006，并同时打印焊接前后两个数）。焊接后所有成品都是**单一连通壳体** —— 说明兵器与手掌本来就是长在一起的，「兵器识别失败」是**权重分配**问题，不是拓扑断裂问题。

由此带来：

- 长兵器只在「肩线以上呈孤立细长团块」或「远离身体前方」时能被自动识别（武松双刀成功；林冲长枪、鲁智深禅杖、花荣弓贴身持握 → 识别失败，兵器按最近骨权重，大幅挥击时会轻微弯曲）。
- 宽体型角色的模板骨架横向偏窄（鲁智深最明显）。
- 披风/战袍跨肩到地被多骨共牵，腿部旋转须 ≤0.3rad，否则下摆被撕成扇形（`skill` 幅度已按此封顶）。

### 8.4 推翻 §8.3 的处方：不是「判据太严」，是「骨架姿势不匹配」（2026-09-13 深夜实测）

§8.3 把失败归因为「种子门控过严」，推荐放开设种的 `d_body > 0.15`。**这条处方是错的**，实测逐条否掉。

**证伪 1：放开种子门控会让结果更差。** 用 `tools/prop_detect_probe.py` 在同批模型上对比两种参考集
（现行 `_d_body` = 躯干+腿+肩+上臂；提议 `d_trunk` = 仅躯干+腿）：

| 林冲单图右手 | 种子数 | 洪泛结果 | 判定 |
|---|---|---|---|
| 现行 `dh<0.10 & d_body>0.15` | **7** | —（种子不足 10，直接跳过） | ❌ |
| 提议 `dh<0.12 & d_trunk>0.12` | **1665** | n=10913、跨度 1.0（吞下整个人）、长细比 2.6 | ❌ 仍丢弃 |

→ 放宽种子只是把失败点从「种子数」搬到「形状校验」，**没有任何净收益**。

**证伪 2：算术根因是「真实的手不在骨架手的位置」。** 右手邻域（`d_hand<0.12`）共 6149 个顶点的
`d_full` 直方图：`<0.06:1026 / 0.06-0.10:2584 / 0.10-0.12:1410 / 0.12-0.15:761 / >0.15:仅 368（6%）`。
`>0.15` 这道门砍掉了 94% 的手部 —— 因为垂手的 Hand 骨就贴在 UpperArm 尾端下方 0.18，肩/上臂把 `_d_body` 拉到 0.06–0.15 区间。

真正的原因是**姿势**：硬编码骨架假设「双臂自然垂放」（`Hand.L/R` 在 z 0.43–0.49），
而生成模型是**右手抬起斜握长矛**的架势（目视 `assets/models/lin_chong_ai_preview.png`：右手握杆在胸腰高度、矛头过头顶、矛尾及地；左手自然垂放）。
真实握持手 ≈ (x −0.25, z 0.59)，距模板手骨 **0.17**（≈ 身高 17%）→ `d_hand < 0.10` 永远圈不到真手。**这才是「种子恒为 6–7」的算术原因。**

**证伪 3：硬编码手骨邻域里根本没有武器。**
镜像不对称度 `asym[i]` = 顶点到「最近镜像点」的距离（**注意实现**：必须是 `kd.find(原坐标)` 去查镜像点云；
若写成 `kd.find(镜像坐标)`，镜像的等距性会让它退化成"到最近顶点的距离"、恒为极小 —— 这个 bug 我踩过，得出过"网格完全对称"的伪结论）。
实测右手硬编码手骨邻域内 `asym > 0.05` 的顶点数 = **0**。

**唯一有效的替代判据（部分可用）：镜像不对称簇。** 把「一侧有、另一侧无」的顶点聚类并渲染
（`tools/prop_detect_viz.py`，输出 `/tmp/propviz/<模型>_{front,right,left,top}.png`）：

| 角色 | 武器 | `asym` 抓到什么 | 可用性 |
|---|---|---|---|
| 林冲（单图/多视图） | 右手斜持长矛 | **矛头+红缨**（杆身中下段被袍角的镜像位置遮蔽 → 看不见） | 只有一段 |
| 鲁智深 | 左手竖持禅杖 | **整根**（月牙铲+杆+杖尾） | 可用 |
| 花荣 | 斜持长弓 | **整张弓**（含弓弦） | 可用 |
| 武松 | **双手各持一刀** | **0 个顶点**（网格精确左右对称） | ✗ 不适用 |

两个必须知道的副作用：
1. `asym` 同样会抓到**因另一臂姿势不同而"多出来"的那条自由手臂**（长管状，长细比/截面形状判据都拦不住）。
   可用「簇内顶点到**手臂链骨架**距离的**中位数**」分开：真矛 0.155/0.174 vs 垂放左臂 0.078/0.091，门槛 0.12。
2. 沿主轴延伸会在非武器区串出**假长条**：林冲单图出现「靴子+袍角+肩甲」沿 x≈−0.07 的竖直线连成
   0.807 长的假簇（z 分片显示其 z 0–0.55 段质心 x=−0.07/**y=+0.07 在身体后方**，根本不是矛杆）。
   可用「簇内距腿骨 <0.06 的顶点占比 ≤3%」挡掉（该假簇实测 4.6%）。

**为什么最终没有落地这条判据**（`tools/prop_detect_viz2.py` 的**逐簇配色渲染**是唯一看清真相的手段）：
把簇 0 涂红、簇 3 涂蓝后一目了然 —— 蓝 = 矛头+红缨+握持的手（对），红 = 靴子+袍角+肩甲（假）。
**杆身仍拿不到**，于是结果是「矛头随手动、杆身不动」→ 挥击时**兵器会从中间撕断，比完全不绑更糟**
（完全不绑只是空挥）。所以 **P2（asym 路径）不上线**，`blender_rig_character.py` 保持原样。

**结论：兵器识别不是判据问题，是骨架姿势问题。** 硬编码骨架的四肢位置与生成模型的架势不符，
这一条根因同时解释三件事：① 兵器识别失败；② 手臂动画"空挥"（权重全落在模板手附近，真手没有骨）；③ 肘/膝错位导致蒙皮变形。
**推荐下一条路：给骨架做「手臂链姿势拟合」** —— 从网格里拟合出真实的手/肘位置再回写骨架（关键难点：兵器与手臂相邻会污染拟合，需鲁棒拟合/修剪）。
拟合一旦成立，现有那套「手部半径 0.10 + 空间洪泛」的简单规则会重新生效，且顺带修好手臂动画。

**判据的最终取值（供续做参考）**：`asym>0.05 & |x|>0.02` 作种子、聚类 r=0.05、n≥80；
形状门限 `长度≥0.35 & 长细比≥3 & n≤5000 & 宽度≤0.22`；再加三道护栏
`离手≤0.35` / `到手臂链距离中位数≥0.12` / `贴腿骨(<0.06)占比≤3%`。

### 8.5 第二批 8 人实测：种子数**不能靠「形态像不像」预判**（2026-09-14）

**三条约束：**

1. **持械手握位必须在腰胯高度（约身高 0.43–0.49）。** 骨架手骨固定在 `x=±0.11, z=0.43–0.49`，种子门槛是「到该骨段 < 0.10」；手抬到胸口（`z≈0.70`）就差 0.2 以上 → **种子恒为 0**。这是安道全 / 吴用 / 李逵三例的共同死因。
   → 标准写法：**「双臂自然垂放于身体两侧、握位在腰胯高度」**。
2. **兵器顶端不得超过头顶。** 归一化用的是**含兵器**的 `maxs.z - mins.z`（见 §6 脚本第 48–59 行），**不单独识别人体高度**。兵器一过顶，人物在归一化空间里被压缩，而骨架坐标按「人体=1.0」硬编码 → 上下全错位。
   → 长兵器一律写死「**朝上、顶端不超过头顶**」。**注意这条会与「长枪过顶更威武」的美术直觉冲突** —— 以管线为先。
3. **兵器必须远离一切大面积布料**（下摆 / 围裙 / 披风 / 马尾）。失败模式**不是「找不到种子」，而是洪泛从兵器窜进相邻布料** —— 扈三娘种子 178（比成功的戴宗还多）照样被判丢弃。
   → 对策是**间隙**：让洪泛的 `_d_body>0.12` 阻断生效。

**推论：竖持是当前唯一被验证能识别的持械姿态**（`dai_zong` = 单手持、垂臂、握在腰胯、兵器竖贴体侧、不加布料）。所以当「姿态多样性」与「管线安全」冲突时**取后者** —— 战斗里角色只有约 1/10 屏高，姿态差异几乎看不见，而兵器撕裂是观感灾难。差异化交给**体格 + 武器形制 + 配色**。

#### 机制 A：**空的「空手侧」反而成了种子源，而且洪泛拦不住**

最反直觉的一条：**持械手拿不到种子，空着的那只手反而拿了一堆。**

| uid | 空手侧 | 持械侧 |
|---|---|---|
| `song_wan` | **346** | **0** |
| `shi_yong` | **258** | **8** |
| `gong_wang` | **373** | 15 |

**原因**：持长兵器竖在体侧时，**手臂要略微外展让开兵器**，手便离开模板手骨；而**空手自然垂在腿侧，恰好落在模板位置**（`Hand.L/R` 是按窄身垂手写死的 x=±0.11、z=0.43–0.49）。**体格越宽偏得越远**：杜迁极瘦 → 持械手 38 种子干净命中；宋万极宽、石勇壮实 → 0 / 8。

**洪泛随后从空手沿前臂窜进战袍**（宋万吞 6949、石勇吞 16903 顶点），因为：

> `BODY_BONES = TORSO | LEGS | {Shoulder.L/R, UpperArm.L/R}` —— **`Forearm.*` 与 `Hand.*` 不在其中**。
> 前臂/手的几何离最近「躯干骨」的距离可以 >0.12，于是 `_d_body > 0.12` 这道阻断**拦不住它顺着前臂往上爬**。

**这些泄漏本轮都被丢弃了，所以无害**（宋万靠 6000 顶点上限、石勇/孙二娘靠长细比）—— 但**是运气不是设计**：宋万的 `elong` 正好 3.0，门槛是 `<3.0` 才丢，差一点就会把 6949 顶点的袍子**刚性绑到空手上**。

#### 机制 B：`elong ≥ 3.0` 太松 —— 会产出「假阳性」

`gong_wang` 以 `elong` 4.3「通过」了，但 `dims[2] = 0.233`（相对身高）≈ **40 cm 厚**，对一根投枪是荒谬的（杜迁 0.051）。渲染帧（`/tmp/rig_gong_wang_{idle,attack}.png`）证实：**attack 帧脚下那块深色片状几何被手骨拖着一起摆动** —— 簇把靴子/腿部一起吞了，再 100% 刚绑到手骨。

> **建议加第 4 条判据：`dims[2] < 0.10`（相对身高）才算干净。**
> 按此重判：`du_qian` 0.051 ✅ / `gong_wang` 0.233 ❌ / `ding_desun` 0.099 ⚠️ 边缘。

#### 结论：姿态窗口**必要但不充分**

三条约束能解释并改善一批失败（杜迁从「不可识别」变成 17.3），但**挡不住机制 A/B** —— 因为根因始终是 **§8.4 那个：模板骨架按「窄身、双臂自然垂放」硬编码，而持械姿势必然偏离它**。宽体格 + 持械外展 = 手必然落在模板之外，**这是提示词层面无法根治的**。
→ **「手臂链姿势拟合」的必要性被这轮数据大幅加强**：它一次同时修好 ① 持械手落空（机制 A 的成因）、② 空手侧泄漏（拟合后手骨就在真手位置，种子不再乱落）、③ 前臂不属 `BODY_BONES` 导致的洪泛外泄。
